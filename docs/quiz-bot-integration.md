# Тест → бот: требование к дизайну и реализации бота

Дополнение к `docs/design-bot.md`, написано после того, как финальный дизайн бота был отдан в работу. **Обязательно к реализации.** Источник: `docs/quiz-spec.md` (тест на лендинге), решение владельца от 2026-09-18 («это начало движения в этот бот»).

## 1. Deep link

Человек проходит тест на лендинге и уходит в бота по ссылке:

```
https://t.me/ensoma_robot?start=q<сумма>
```

где `<сумма>` — сумма семи ответов, целое 0…70 (например `?start=q42`).

Telegram доставит это боту как первое сообщение `/start q42` (payload — второй аргумент).

## 2. Что делает бот

- Парсит payload регулярным выражением `^q(\d{1,2})$`. Валиден, если число в диапазоне 0…70.
- Сохраняет на пользователе: `quiz_sum` (0…70), `quiz_index` = `Math.round(quiz_sum / 70 * 100)`, `quiz_at` (время).
- Невалидный или отсутствующий payload → `quiz_sum = null`, обычный онбординг, **ничего не спрашиваем и не упоминаем**. Бот никогда не просит человека «сначала пройти тест».
- Повторный `/start` с payload у человека, который уже в программе: индекс **не перезаписываем** (первый замер — точка отсчёта), но сохраняем в журнал событий. Исключение: программа уже завершена и человек начинает заново — тогда новый индекс становится точкой отсчёта нового круга.

## 3. Где это видно человеку

**Ровно один раз, в онбординге**, после приветствия и до вопроса про удобный час. Если `quiz_sum` есть:

> Твой индекс опоры сейчас {quiz_index} из ста. Это точка отсчёта, к ней вернёмся через семь вечеров.

Если `quiz_sum` нет — этой строки просто нет, остальной онбординг не меняется. Никаких «ты не прошёл тест», никаких ссылок на лендинг.

Тон и формат — как у остальных сообщений бота (на «ты», без восклицательных знаков). Текст должен быть в списке редактируемых в админке сообщений под ключом `onb.quiz_index` с плейсхолдерами `{quiz_index}`, `{quiz_sum}`.

## 4. Финал седьмого вечера

На седьмом вечере, **после** графика и итога «было / стало», если `quiz_sum` есть — предложить повторить тест, **по кнопке, не навязывая**:

> Семь вечеров назад твой индекс опоры был {quiz_index}. Хочешь посмотреть, что с ним сейчас?
> [ Пройти семь вопросов ] [ Не сейчас ]

По кнопке «Пройти семь вопросов» бот задаёт те же семь вопросов из `docs/quiz-spec.md` **внутри Telegram**: один вопрос за сообщение, ответ — inline-кнопками 0…10 (две строки: 0–5 и 6–10), под вопросом теми же двумя подписями, что на сайте. Прогресс «3 / 7». Кнопка «назад» на каждом шаге, кроме первого.

После седьмого ответа:

> Было {quiz_index_before}. Стало {quiz_index_after}.
> {текст результата — один из пяти, дословно из quiz-spec.md}
> Это не диагноз и не оценка твоей личности. Это фотография твоего состояния сегодня.

Сохраняем как второй замер: `quiz_sum_after`, `quiz_index_after`, время. «Не сейчас» — закрывает предложение навсегда (больше не спрашиваем), путь идёт дальше к приглашению на разговор.

Дисклеймер под результатом — **обязателен всегда**, и в боте тоже.

## 5. Админка

- В таблице людей — колонка «Индекс» вида `60 → 74` (или `60 → —`, если повторного замера нет).
- В карточке человека — оба замера с датами и все 7 ответов каждого замера (чтобы специалист видел, какой именно вопрос сдвинулся).
- На дашборде — средний индекс на входе, средний на выходе, средний прирост индекса по тем, кто прошёл оба замера, и число прошедших второй замер. Считать только по людям с двумя замерами.
- Тексты пяти результатов и семи вопросов — редактируемые (ключи `quiz.q1`…`quiz.q7`, `quiz.q1.low`/`quiz.q1.high`…, `quiz.result1`…`quiz.result5`, `quiz.disclaimer`), значения по умолчанию — дословно из `quiz-spec.md`.

## 6. Схема БД (дополнение к `docs/architecture.md`)

```sql
-- на users:
quiz_sum         INTEGER,      -- 0..70, входной замер, NULL если пришёл без теста
quiz_index       INTEGER,      -- 0..100
quiz_at          INTEGER,      -- unix ts
quiz_sum_after   INTEGER,      -- повторный замер в боте после 7-го вечера
quiz_index_after INTEGER,
quiz_after_at    INTEGER,
quiz_after_declined INTEGER DEFAULT 0,  -- нажал «Не сейчас»

-- отдельная таблица с поответными данными (нужна админке):
CREATE TABLE quiz_answers (
  id        INTEGER PRIMARY KEY,
  user_id   INTEGER NOT NULL REFERENCES users(id),
  phase     TEXT NOT NULL CHECK (phase IN ('before','after')),
  q         INTEGER NOT NULL CHECK (q BETWEEN 1 AND 7),
  value     INTEGER NOT NULL CHECK (value BETWEEN 0 AND 10),
  created_at INTEGER NOT NULL,
  UNIQUE (user_id, phase, q)
);
```

Входной замер приходит одной суммой (поответных данных с лендинга нет — лендинг ничего не отправляет на сервер), поэтому `quiz_answers` с `phase='before'` заполняется только если человек проходил тест внутри бота. Админка это учитывает: показывает «поответно» там, где данные есть.

## 7. Граничные случаи

| Случай | Поведение |
|---|---|
| `?start=q0` | Валидно. Индекс 0. Ничего не подсвечиваем как «плохое». |
| `?start=q70` | Валидно, индекс 100. |
| `?start=q71` и больше, `qabc`, пустой payload | Игнорируем молча, обычный онбординг. |
| Человек прошёл тест, но не дошёл до 7-го вечера | Повторный тест не предлагаем. Индекс остаётся в админке как есть. |
| Человек пришёл без теста и дошёл до 7-го | Повторный тест **не предлагаем** (не с чем сравнивать). |
| Человек начал повторный тест и бросил на 4-м вопросе | Ответы сохраняются, при следующем контакте бот один раз мягко предложит продолжить: «Осталось три вопроса. Продолжим?» Второй раз не напоминает. |
